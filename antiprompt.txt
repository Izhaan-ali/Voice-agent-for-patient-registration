# Voice AI Patient Registration

## Complete Implementation Specification

## 1. PROJECT OBJECTIVE

Build a voice-based AI patient registration system that can be accessed through a real, dialable U.S. phone number.

A caller should be able to call the number and naturally provide their demographic information through conversation.

The system must:

1. Answer an incoming phone call.
2. Conduct a natural conversation with the caller.
3. Collect required patient demographic information.
4. Handle corrections, clarifications, different ways of saying information, and out-of-order information.
5. Validate information.
6. Re-prompt specifically when a field is invalid.
7. Summarize all collected information before saving.
8. Ask the caller for confirmation.
9. Persist the confirmed patient record in a database.
10. Expose patient records through a REST API.
11. Preserve data across server restarts and subsequent calls.
12. Support a second call where previously registered information can be recognized.
13. Handle important failure cases gracefully.
14. Be deployable and callable for evaluation.

Do NOT build an over-engineered production healthcare platform.

The goal is a reliable, understandable end-to-end technical assessment implementation.

---

# 2. ASSESSMENT REQUIREMENTS

The system must satisfy the following core requirements.

## Voice

Use Vapi as the voice/telephony platform.

The caller must be able to call a real U.S. phone number.

The conversation must be natural rather than a rigid IVR flow.

The agent must:

* understand varied phrasing;
* ask clarifying questions;
* handle corrections;
* handle information provided out of order;
* validate required information;
* specifically re-prompt invalid fields;
* confirm all collected information before saving;
* handle caller requests to start over;
* gracefully handle database/API failures.

## Database

Use SQLite for the assessment implementation.

Data must survive:

* application restart;
* server restart;
* subsequent phone calls.

Use SQLAlchemy for database access.

## Backend

Use:

* Python
* FastAPI
* Pydantic
* SQLAlchemy
* SQLite

Expose the required REST endpoints.

## Voice-to-backend integration

Vapi should call the FastAPI REST API after the caller confirms the patient information.

Prefer Vapi's API Request Tool for the primary integration.

Do not build a custom STT/TTS pipeline.

# 18. VALIDATION BEHAVIOR

Validation should happen at two levels.

## Level 1 — Conversational validation

The LLM should detect obvious invalid input.

Example:

Caller:
"My phone number is 123."

Agent:

"That doesn't appear to be a complete U.S. phone number. Could you provide your 10-digit phone number?"

Do not proceed with invalid information.

---

## Level 2 — Backend validation

FastAPI/Pydantic must independently validate everything.

Never trust data simply because the LLM produced it.

This is critical.

# 19. REQUIRED EDGE CASES

Implement at least these:

## Invalid phone

Caller gives:

"123"

Agent requests the field again.

---

## Future DOB

Caller gives a future date.

Agent says the date appears to be invalid because it is in the future and asks again.

---

## Incorrect state

Caller says:

"California"

Agent can normalize it to CA if unambiguous.

If ambiguous:

ask clarification.

---

## Caller corrects information

Caller:

"My last name is Smith."

Later:

"Actually, sorry, it's Smyth."

The latest confirmed value should replace the previous value.

---

## Caller gives information out of order

Caller:

"I'm John Smith. I live in New York. My birthday is..."

Agent should store known information and continue asking for missing fields.

---

## Caller wants to start over

Provide a natural restart path.

Example:

"Sure. Let's start over."

Clear temporary conversation state.

Do not delete an already-created database record unless explicitly required.

---

## Database failure

If POST /patients fails:

Do not tell the caller registration succeeded.

Say something like:

"I'm sorry, I wasn't able to save your registration right now. Please try again later."

Log the technical failure.

---

## Call disconnect

If the caller disconnects before confirmation:

Do not create the patient record.

If they disconnect after successful persistence:

the record should remain.
